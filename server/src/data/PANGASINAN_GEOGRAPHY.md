# Pangasinan registration reference data

`pangasinanBarangays.json` contains public names and PSGC codes for 1,364 barangays in the application's existing 48 cities and municipalities. It contains no citizen information or street/address records.

Downloaded October 17, 2026:

- Municipality hierarchy: https://psgc.cloud/api/v2/provinces/pangasinan/cities-municipalities
- Barangays: https://psgc.cloud/api/v2/provinces/pangasinan/barangays
- Independent mirror used to cross-check all 1,364 ten-digit codes: https://psgc.gitlab.io/api/provinces/015500000/barangays/
- Underlying classification: Philippine Statistics Authority, https://psa.gov.ph/classification/psgc

PSGC Cloud and PSGC GitLab are community services derived from PSGC; this snapshot is not represented as a direct, authenticated PSA API download. The API retrieval date is recorded, rather than claiming a release quarter that the response did not specify. Retain source attribution when updating or distributing this reference.

Transformations are limited to projecting names/codes, trimming outer whitespace, alphabetical sorting, grouping barangays by their seven-digit municipality prefix, and mapping city-label forms to the existing SafeLink labels. Existing municipality names and ZIP codes remain in `pangasinanLocations.js`; ZIP values from the downloaded sources were not substituted. No barangays were invented.

To refresh, fetch the two PSGC Cloud resources, compare the complete ten-digit barangay-code set with the second mirror, apply the same transformations, and review changes before replacing the snapshot. Validate all 48 municipality keys against the existing dataset, unique codes and names, and lookup of every barangay. In a non-production environment, check dependent municipality/barangay choices and street suggestions, including missing-provider and manual-entry behavior. The runtime-only project no longer contains the historical automated suites; arrange separate regression verification when changing this reference. Updating the reference file does not change user records.

Street names are not part of PSGC. The separate street-suggestion service queries public OpenStreetMap named roads inside the selected municipality/barangay boundaries through Overpass. No streets are inferred from citizens or incident records. Missing boundaries, missing mapped names, or provider outages result in manual entry rather than invented suggestions. Attribution: https://www.openstreetmap.org/copyright. Provider documentation: https://wiki.openstreetmap.org/wiki/Overpass_API.

Do not use the public Nominatim endpoint for autocomplete; its policy prohibits that use: https://operations.osmfoundation.org/policies/nominatim/.

Incident address detection uses an authenticated POST to `/api/locations/incident-address` after the Citizen clicks Use Current Location or selects a map point. Valid coordinates trigger lookup regardless of GPS accuracy (including unknown accuracy); there is no 100 m GPS cutoff. Optional nonnegative `accuracy` is sent in the POST body, never the URL. The server uses the existing incident boundary, exact normalized names in this snapshot, and the existing municipality ZIP table. Remote street/POI results (over 100 metres from the requested point) are omitted; this is a nearest-feature distance check, independent of GPS uncertainty. Detected fields and unresolved fields are listed separately, with the approximate GPS accuracy and a request to verify the barangay and pin.

Barangay names alone are insufficient: autofill additionally requires a provider administrative boundary (`category=boundary`, `type=administrative`, `admin_level=10`), its name matching the municipality-scoped canonical barangay, and its Polygon/MultiPolygon containing the full GPS uncertainty disk with a two-metre clearance margin. Polygon holes and all edges count toward clearance. Unknown GPS accuracy, overlapping an edge, absent geometry, road/POI geometry, a bounding box alone, mismatched names or missing tags leave the barangay blank for manual confirmation. Requests ask for unsimplified GeoJSON and extra tags on the returned reverse-geocoding object. Nominatim returns one nearest object, so a typical road result does not supply a barangay boundary; no boundary is inferred or fetched through unbounded follow-up calls. This is conservative validation of available OSM boundaries, not certification against a government cadastral survey. A manually adjusted pin is checked with zero GPS uncertainty and still requires boundary evidence. Citizens must review the address and can select their barangay manually.

Cached provider results are reassessed for each requested coordinate and accuracy; neither a previous precise fix nor an in-flight lookup can authorize an uncertain barangay later. Manual corrections cancel pending results. Changing municipality clears the old barangay, street, landmark and pin, refreshes barangay options and supplies the existing municipality ZIP. Lookup and failure caches remain memory-only, and accuracy is not added to submitted incident records.

The Nominatim-compatible provider is configurable through server-only `REVERSE_GEOCODING_URL`. The default public endpoint requires a maximum of one request per second **across the entire application**, identifying User-Agent, attribution, caching, moderate traffic, and explicit user actions. This service allows only one upstream request in flight per process, spaces starts at least 1.1 seconds apart, deduplicates identical requests, and retains at most 100 short-lived results in memory (10 minutes; failures 30 seconds). It returns busy feedback rather than queueing unlimited work. Deployments with multiple replicas need a shared throttled proxy or a suitable provider; per-process limits do not enforce a distributed quota. No lookup records, precise-location logs, or database writes are introduced. Coordinates are sent to the selected provider for address lookup. Provider documentation: https://nominatim.org/release-docs/latest/api/Reverse/.
